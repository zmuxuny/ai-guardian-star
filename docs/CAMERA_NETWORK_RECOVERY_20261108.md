# 摄像头网络卡顿与自动恢复修复

## 结果和原因

本次修改手机预览的两个源码文件，并在实际故障复现后增加板端FRP的一项探活配置。网络抖动本身未被消除，改动解决短暂断流后的额外固定等待，以及失效转发连接检测间隔过长的问题。

已有实测：开发板本地流14.16fps、最大帧间隔149ms；开发板到云端10次ping全部返回，但RTT为22.899～549.200ms，平均112.392ms。视频FRP连接的TCP状态存在累计重传，不能把累计计数当成本次测量的丢包率。开发板使用Wi-Fi出口，不能仅凭地址断言热点或运营商类型。

被动读取现有云端共享帧槽35秒：698次响应均为200，本地HTTP请求p50=0.70ms、p95=1.10ms，云端收帧后年龄p95=111ms、最大204ms。没有额外建立第二路公网视频流。因此有网络波动证据，但本窗口没有复现长时间断流，也不能宣称所有卡顿都来自同一原因。帧年龄不是采集到显示的物理延迟。

原客户端连接/读取超时均5秒，失败后固定等待800ms；服务端表示暂时无新帧的204也会抛出异常。短暂网络故障后，这些等待会推迟恢复。

## 最小修改

- `entry/src/main/ets/common/CameraFrameClient.ets`：连接/读取超时分别缩至1500ms；204不解码、不抛连接错误，继续等待新帧。503、坏图和真实网络错误仍按失败处理，资源照常释放。
- `entry/src/main/ets/components/CameraStreamView.ets`：网络失败按200/400/800/1500ms重试并封顶，收到HTTP正常结果后重置。正常取图仍按67ms目标节奏执行。已有画面2秒没有新帧会显示既有中断提示；新帧到达立即清除提示。首次连接仍有10秒提示宽限。
- 原有单请求、序号去重、退出取消、代际隔离和位图释放保留。没有修改模型、人脸库、录像、码率或云端持久配置。
- 第一轮用户仍反馈长时间无法恢复，恰逢云端服务active、帧年龄3401ms/204、开发板SSH转发同时关闭，随后视频和SSH共同恢复。不能把手机端受控测试通过当成真实问题解决。
- `24fe05d`：板端FRP0.61.1实际配置没有transport设置，仅增加 `transport.tcpMuxKeepaliveInterval = 5`。该版本默认30秒，原字段/运行机制已对照[同版本配置源码](https://github.com/fatedier/frp/blob/v0.61.1/pkg/config/v1/client.go)、[连接实现](https://github.com/fatedier/frp/blob/v0.61.1/client/connector.go)。不改变协议、token、代理端口或服务端参数；不宣称网络丢包会消失。

源码提交：`504f6f7`、配置提交 `24fe05d`，分支 `wip/codex-20261108-camera-network`，已推送。未合并zy。原有无关本机改动保留。

执行顺序为：备份 → 最小修改 → 本地测试/构建 → 提交推送 → 手机覆盖安装与受控测试。

- 本地Git回退点：`backup/camera-network-before-20261108`。
- 原安装包：`.tmp/camera-network-20261108/rollback-entry-default-signed.hap`，24,697,840B，SHA256 `04D9DA0A97A0C119E0F63EED3AB2D1C03F7145DAF0C5073E12A03D1CC5B3C6C9`。
- 云端备份 `/root/backup/camera-network-20261108/`：原预览脚本、systemd unit及Nginx站点配置。
- 板端同名备份目录：原识别主程序、板端HTTP程序、视频程序、预览参数drop-in，以及原`frpc-aliyun.toml`和对应service。板端应用源码未修改。
- 隧道配置需回退时，将该目录的原`frpc-aliyun.toml`恢复到 `/root/frp_0.61.1_linux_arm64/frpc-aliyun.toml`，以现有FRP二进制verify通过后重启`frpc-aliyun.service`。本次部署预设90秒板端自动恢复原配置，只有确认SSH/视频恢复、配置为5秒后才取消回退定时器。
- 手机需回退时，以HDC对指名USB设备执行 `install -r` 安装上述旧HAP，再启动原应用；不卸载、不清数据。源码回退用revert本次逻辑提交，保留无关修改，不执行reset/clean。
