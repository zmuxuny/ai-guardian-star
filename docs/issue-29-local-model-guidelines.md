## 目标和职责边界

- 目标是能跑、能演示、团队自己能复现的版本，不追求专业指标。模型选型、运行方式、提示词和语音接入方式由本地模型负责人决定。
- 本地模型由 zhouyang 负责；个性化模块由 gufeng（`@gufeng35`）负责。模型只负责问候、对话和回答理解；是否提醒、通知 App／家属或报警由个性化规则决定。
- 模型不得直接修改个人基线、阈值或反馈训练数据；对话理解结果不自动等同于误报／漏报反馈。接入现有 care 链路时沿用稳定事件 ID，经适配层接入，保留现有模式门禁。
- 项目已有姿态检测、人脸识别、录像、语音播报和 MQTT 告警；实施前核对实际分支与部署情况，优先复用，不因本任务擅自合并其他分支。

## 交付顺序与时间

1. **2026 年 12 月底前试跑**：开发板试 1～2 个小模型，记录回答速度、内存占用，以及与检测服务并行运行时是否卡顿；给出板端可用还是需要云端的结论。不能用单独运行模型的结果代替并行验证。
2. **2027 年 1～4 月能对话**：优先实现断网可用的文字简单问答；语音为进一步接入项。响应速度以实测和演示可接受为准，当前没有约定硬性性能数值。
3. **2027 年 5～8 月问候与理解**：接收个性化提醒，生成一句问候，理解回答并回传；模型过慢或报错时使用固定话术，不能卡住流程。同阶段配合板端定期记录时间、区域、状态，供个性化模块后续使用真实作息数据。
4. **2027 年 9～11 月联调和演示**：两模块联调，录制拔掉网线后完成一次问答的视频。

若板端确实跑不动，依据试跑证据改用云端完成对话、问候理解和兜底，并写明原因。云端方案不能宣称通过板端断网问答验收；演示范围的变化须明确记录。

## 两人对接与消息基准

- 原任务要求第一周共同确定消息格式并放入 `docs/`。目前以已采用的 v5 为后续实现和首轮联调基准；不能退回下载目录中的旧稿，也不能把用户采用视为其他协作者已确认全部参数。
- 个性化模块发送提醒类型、时间、理由；本地模型回传回答意思。v5 已细化为 `ok`、`needs_help`、`unclear`、`no_response`，并单列流程 `error`，不得压缩回只有三类或将故障伪装成无回答。
- 可先用假提醒调问候；个性化方可先用固定话术跑流程，双方互不等待。模拟通过只证明对应流程，不证明真实模型、语音、设备或 App 链路通过。
- 按 v5 落实事件关联、过期检查、次数和总时限、求助优先、版本去重、事务持久化、补发及重启恢复。具体参数与接口以基准正文为准，不在此另建一套数值。
- v5 的 HTTP 路径是待实现约定，不能当作现有 API 直接调用；联调前与对方确认版本、路径和参数。HTTP／MQTT 接收确认不代表老人已回答、报警完成或 App 已收到。
- 作息记录点只采集实际可支持的时间、区域与状态（站／坐／躺／不在等）；接入时确认采样和数据约定，不把区域观察直接解释为疾病或身体状态。
