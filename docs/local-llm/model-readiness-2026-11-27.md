# 模型预热与就绪门禁

本轮按用户“继续下一步”实施预热和就绪控制，基于zy@8594dc2的独立分支`wip/codex-20261127-model-readiness`，不合并或改写未合并的[PR #34](https://github.com/zmuxuny/ai-guardian-star/pull/34)。该PR中的冷启动分类失败保留，本次将准备成本移到接收新提醒之前，而非宣称消除了冷启动耗时。

## 实现与协议边界

- 新增`src/local_model_readiness.py`：进程内cold/warming/ready/failed状态，30秒预热再5秒探测，复用同一SemanticIntentClient的完整SSE与语义JSON校验。探测完成只说明传输和缓存准备，不代表理解质量。
- `serve --role model`真实模型模式默认后台预热。`GET /health/ready`在未就绪时503、就绪时200，返回准备耗时及分阶段调用计数；新提醒在未就绪时503且不占问答名额。去重和格式校验优先，已有提醒仍可duplicate，过期/冲突按原协议处理。
- 后端请求串行，分类失败撤销就绪；单后台工作者重试，失效的准备任务不能发布陈旧ready，非协作后端不会累积线程。每次服务启动都重新准备，不从数据库读取旧ready。再次准备失败时继续拒收新提醒。
- `prepared_session`由真实CLI和板端验证共用。固定问候、V3分类规则、结果版本、求助保持和补发协议不变。已接收待启动事件在准备期间仍检查90秒总时限和提醒有效期。
- 复审发现故障后等待追问的pending事件会拒绝明确求助，已补失败回归并修正：已展示过问候的pending仍可接收文字，明确规则求助不依赖模型；重启时这种pending应回interrupted，不能伪装首次启动重播。

显式`--simulate`和peer角色不做模型预热。旧`demo`命令保留为PR #33的原始直接后端演示/对照，不应用本服务门禁；验证门禁应运行真实`serve`或本报告的受控场景，不应把原始demo路径当成已门禁化的服务。所有入口仍只绑定回环地址，未接生产care/报警。

未验收：任意长度/前缀输入均5秒内的保证、长期资源稳定、真实个性化/生产care/App、模型生成问候、语音、物理断网断电、窗口外独立求助入口。V3已知否定误报和安好弃权仍保留。代码和证据通过新PR交付zy，不自行合并或部署生产。

就绪表示最近一次准备探测成功，不是永久健康保证。服务进程重启会从cold开始；外部模型停机/重启目前由后端调用失败发现并撤销ready。若模型快速重启且没有调用观察到故障，下一次回答仍可能先触发5秒澄清兜底，不能宣称能即时识别所有模型重启。
