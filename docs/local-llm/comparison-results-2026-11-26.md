# 1.5B 与 0.6B 新样本同条件对照及首版研究选型

日期：2026-11-26，Asia/Shanghai。对应 Issue #29，承接已合并 PR #30。真实连接开发板，完成全部4段、72个正式请求及8个独立诊断请求；进程退出码0。没有部署生产功能。

## 选型结论

**首版文字研究默认选择 Qwen2.5-1.5B-Instruct / Q4_K_M。Qwen3-0.6B / Q8_0 保留为速度对照，不作为当前分类提示配置下的默认。**

1.5B 对同组36条正确24条，能区分本组全部12条明确求助和12条明确无需帮助。0.6B 正确12条，35/36条都输出needs_help，其中全部12条无需帮助均被误报。0.6B快约一半、内存更低，但当前表现更接近偏向单一类别，不能把这一偏向当成理解可靠或安全通过。

这是有代价的研究选择：1.5B有5条不确定输入被错判okay，比0.6B的1条更多；它并非所有关键指标均优于0.6B。两者都没有正确识别本组任何一条unclear，均不符合直接接入正式关怀判断的要求。选择1.5B是因为它在当前共享提示下保留了明确正向/求助的区分能力，适合作为下一步研究起点，不是因为风险已经解决。

后续先处理不确定/转述/控制命令的边界及5秒预算余量，再以新的冻结样本验证；不让模型单独裁决报警或解除告警。正式v5接口、语音或其他提示配置仍需另验，本轮不冻结这些接口或宣布上线。

## 理解质量

**1.5B：24/36（66.7%）。** 求助12/12，无需帮助12/12；12条不确定全部错误，其中5条okay、7条needs_help。错误求助7条，明确求助漏判0条。

**0.6B：12/36（33.3%）。** 求助12/12，无需帮助0/12；12条不确定全部错误，其中1条okay、11条needs_help。错误求助23条，明确求助漏判0条。输出needs_help共35次，因此“错误okay只有1条”不能单独解释为较好的理解质量。

两款36次均完整返回合法格式，没有正式请求超时或格式错误；错误没有从分母剔除。JSON Schema约束仅保证形状，不能保证语义。正式样本中的unclear是真实文本的标签，不是无回答、音频故障或模型异常。

所有逐条输入、独立标签、模型原始JSON、解析结果与耗时均保存，包括不利样例，不仅保留汇总分数。

## 首次响应与预热

每次模型新进程都先使用同一条独立诊断输入；该首次请求本身就是显式预热成本。随后另一条同系统提示前缀的独立输入测预热后响应。诊断输入不来自正式36条，允许60秒，未混入正式准确率或10秒通过数。

- 1.5B，两次进程就绪均约2.517秒；首次完整返回分别14.791、14.976秒，首个非空SSE内容分别13.128、13.285秒；随后完整返回4.001、4.037秒。
- 0.6B，两次进程就绪约2.607、2.544秒；首次完整返回6.450、6.471秒，首内容5.501、5.526秒；随后完整返回2.060、2.070秒。

首次诊断输入是“没有听懂问题”的含糊表达，两款的两次首次诊断均语义错误；此处计时成功不等于诊断分类正确，也不纳入正式分母。

这些是进程就绪及固定提示下的请求时间，未清空系统文件页缓存，不是整板冷启动。SSE首片段一般是JSON片段，不能直接播报或作为已经理解的结果；真正可用的意图要等完整结束及校验。不同提示前缀或真实多轮历史可能重新增加耗时，本轮未覆盖。

## 正式请求耗时与5秒预算

- 1.5B：完整结果中位4.762秒，最慢5.260秒；32/36条在5秒内完成，4条晚于5秒；同时语义正确且5秒内完成22/36。
- 0.6B：完整结果中位2.315秒，最慢2.471秒；36/36条在5秒内完成；同时语义正确且5秒内完成12/36。

以上都是本轮实际10秒总截止下的完整耗时，再按5秒分类预算计数；没有另做一次5秒截断试验，不能把4条超预算声称为实际执行了4次超时回退。两个不同诊断短句的预热后时间也不代替36条正式样本的中位时间。

1.5B的交互余量仍偏小，不能只凭暖请求约4秒承诺所有请求满足v5建议的5秒分类预算。0.6B的速度优势也不能补偿当前配置下的严重误报偏向。
