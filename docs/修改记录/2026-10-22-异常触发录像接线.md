# 2026-10-22：异常触发录像接线

## 问题与修改原因

`5c5afbd` 只交付了模块，服务跑起来不会真的录：

- 没有真实编码后端（`RecordingManager` 要求调用方提供 `backend_factory`）；
- 服务生命周期里没有创建 `HistoryStore` / `EventClipCache`；
- 采集点没有喂帧，告警点没有触发。

上一轮有意不做接线，是因为 `src/ascend_board_server.py`、`src/ascend_main_other.py` 当时躺着他人未提交的 ACL 改动，混在一起无法干净回退。这批 ACL 改动已先单独提交（`64ada8f`），本轮在其之上接线。

## 行为变化

- **默认仍然关闭**：只有设置 `AI_GUARDIAN_RECORDING_CONFIG` 且 `enabled=true` 才会创建存储、启动缓存。未配置时启动日志打印"事件录像默认关闭"，检测链路完全不受影响。
- **录像故障不影响检测**：初始化、喂帧、触发三处都包了异常捕获并限频打印，失败只丢录像，不中断推理/告警主流程。
- 事件触发一次记录，写入 `events` 行；片段完成且 `media_verified` 通过后才写 `event_recordings` 关联，片段失败则不关联（fail-closed）。
- 采集点每帧做一次有界内存拷贝；`pre_roll_seconds=5` 在 640×480 下约占用 5×15×0.9 MB ≈ 67 MB 上限（受 `cache_bytes=32 MiB` 约束实际更小）。

## 本轮修掉的一个真实缺陷

板端第一次跑接线验证时片段 `state=failed`、`linked_events=0`。原因是 `FfmpegSegmentBackend.finish()` 先 `stdin.close()` 再 `communicate()`，而 `Popen.communicate()` 会 flush 已关闭的 stdin 并抛 `ValueError`（它只捕获 `BrokenPipeError`）。修复方式：关闭后把 `proc.stdin` 置 `None` 再交给 `communicate()`，并补了回归测试 `test_finish_drops_closed_stdin_before_communicate`。

离线单测发现不了这个问题，因为假后端不带 stdin 语义——这正是接线级验证的价值。

## 验收中发现的环境问题

- 摄像头设备节点在 15:52 重新枚举：**`/dev/video0` 已不存在，现有 `/dev/video1`、`/dev/video2`**。排查摄像头问题时不能按固定的 `video0` 判断。
- 摄像头当前**朝向天花板**，`/api/stats` 的 `detections` 为 0，关键点置信度极低（head 0.031 / shoulder 0.122）。此时无法验证摔倒/久坐检测，需先调整摄像头姿态。
- `/video_feed` 输出为 **320×240**，而检测器采集为 640×480。即：手机端看到的是降采样流；服务内接线从采集点取帧，录制分辨率是 640×480。两条路径的分辨率不同，不要用 `/video_feed` 的尺寸推断录制尺寸。

## 部署与回退

部署步骤（必须先备份板端目录与数据库）：

1. 备份 `/root/ai_guardian` 与 `db/history.db`（服务运行中要用一致性快照）。
2. 准备录像数据根（独立分区或目录），确保为空或已由本模块初始化；设置 `AI_GUARDIAN_RECORDING_CONFIG` 指向 JSON，`encoder` 填 `"ffmpeg-libx264"`。
3. 确认板端存在 `ffmpeg` 与 `ffprobe`（板端为 4.4.2，含 libx264）。
4. 重启服务，检查日志出现"事件录像已启用 pre=… post=…"，并确认 `/api/stats` 正常、摄像头在线。
5. 制造一次真实事件，检查 `events` 与 `recordings` 是否出现关联、片段可否 `ffprobe` 打开。

回退：删掉 `AI_GUARDIAN_RECORDING_CONFIG` 环境变量并重启，功能即回到关闭；代码回退用 `git revert <提交号>`；`event_recordings` 表可独立 `DROP`，不影响既有 `recordings`/`events` 数据。
