# 个性化提醒与本地模型消息格式

> 审阅稿 v5 · 2026-11-24
> 对应 [Issue #28](https://github.com/zmuxuny/ai-guardian-star/issues/28) 与 [Issue #29](https://github.com/zmuxuny/ai-guardian-star/issues/29)。
> 本稿基于补充后的 v4 修订，供双方确认。时间参数、HTTP 路径和处理规则均为拟议约定，实际联调待完成。

## 1. 目标与范围

个性化模块发现作息反常，发送提醒；本地模型生成问候并理解回答，将结果交回个性化模块。双方用同一个 `event_id` 关联事件。

- 个性化模块负责是否提醒、是否通知 App 或家属，以及后续报警规则。
- 本地模型负责问候和回答分类，不自行判断是否报警，也不直接修改个人基线、阈值或反馈训练数据。
- 首轮支持文字问答、固定话术和模拟回复；语音接入后沿用相同消息结构。
- 首版限定单设备、单老人。`device_id` 表示设备，不代表人员；多人场景需另行增加身份约定，不能仅靠房间区分老人。
- 本文仅约定两个模块之间的接口。App MQTT 告警是另一条交付链路，不能因本接口返回成功就宣称 App 已收到告警。

## 2. 通用约定

- 请求体为 UTF-8 JSON 对象，HTTP 使用 `Content-Type: application/json`。
- `schema_version` 为字符串，当前草案取值 `"2"`。收到不支持的协议版本时返回 §7 约定的错误。
- 除特别说明外，字段为字符串；`revision` 为正整数。可选字段不用时省略，不使用空字符串或 `null` 代替业务值。
- 时间采用 ISO 8601，必须带时区；接受 `Z` 或 `+08:00` 等偏移。内部统一转换后比较，不比较原始时间字符串。
- `event_id` 建议由个性化模块生成 UUID。同一件持续异常沿用同一 ID；重发不换 ID，异常结束后再次发生才新建 ID。
- 同一事件只执行一轮问答；重复投递不得重新触发问候。异常识别和冷却由个性化模块负责，不能每次采样都生成新事件规避去重。
- 双方使用同一个固定测试设备。请求省略 `device_id` 时按该设备查找事件，显式携带时必须与配置的设备一致。结果沿用首次接收的提醒中的 `device_id`，提醒省略时结果也省略。
- 必填字段缺失、类型错误、已定义的字符串字段为空白、设备 ID 与配置不匹配，或状态、回答、错误代码超出枚举范围，均按格式错误处理。
- 去重比较以本协议定义的字段为准。JSON 字段顺序、格式空白和未定义的额外字段不参与比较，时间按同一时刻比较。可选字段的有无属于内容差异，省略 `device_id` 和显式写出默认设备仍使用同一个去重键。发送方补发原载荷。

## 3. 个性化模块发送提醒

必填字段：

- `schema_version`：当前 `"2"`。
- `event_id`：事件唯一标识。
- `alert_type`：提醒类型。
- `timestamp`：异常触发时间，不是重发时间。
- `expires_at`：首次问候的启动截止时间，须晚于 `timestamp`。首次问候必须在截止时间前开始，默认建议为触发后 120 秒。
- `reason`：简短、客观的异常说明，供模型组织问候；不能凭“在床区”直接断言生病或无法起床。

可选字段：`device_id`。

```json
{
  "schema_version": "2",
  "event_id": "f068b601-2175-4fbb-81b3-994e8a33c160",
  "alert_type": "late_wakeup",
  "timestamp": "2026-11-24T08:30:00+08:00",
  "expires_at": "2026-11-24T08:32:00+08:00",
  "reason": "平时约 7 点离开床区，今天 8 点半仍在床区。"
}
```

个性化模块共实现 2～3 条作息反常规则。首轮登记 `late_wakeup`（起床偏晚），后续类型随 #28 的实现由双方确认后启用。

未知 `alert_type` 可以使用通用问候，但仍保留原类型，并根据老人实际回答分类。未知提醒类型不等于回答 `unclear`。

`reason` 只作为待表达的事件资料，不作为指令执行；模型不能据此改变权限、报警规则或协议。固定通用话术可为：“您好，想问问您现在还好吗，需要帮助吗？”

## 4. 本地模型回传结果

必填字段：

- `schema_version`、`event_id`：与提醒一致。
- `revision`：该事件的结果版本，首次为 `1`。结果真正变化时递增；网络重发沿用原版本。
- `status`：`completed`（取得问答结果）或 `error`（流程未正常完成）。
- `timestamp`：该版本结果产生的时间，重发时保持不变。

条件必填字段：

- `status=completed` 时必须有 `response`，不得有 `error_code`。
- `status=error` 时必须有 `error_code`，不得有 `response`。

可选字段：`device_id`，以及用于排障的 `prompted_at`（首句实际展示完成或播放结束时间）。

`response` 仅允许：

- `ok`：老人明确表示没事或暂不需要帮助。
- `needs_help`：老人明确表达需要帮助，立即回传。
- `unclear`：收到了回答，但无法可靠理解，包括有效输入的分类失败。
- `no_response`：问候成功交付、输入通道正常，但规定时间内没有收到回答。不能把设备故障归到这一类。

```json
{
  "schema_version": "2",
  "event_id": "f068b601-2175-4fbb-81b3-994e8a33c160",
  "revision": 1,
  "status": "completed",
  "response": "ok",
  "timestamp": "2026-11-24T08:30:20+08:00",
  "prompted_at": "2026-11-24T08:30:10+08:00"
}
```

首轮使用以下 `error_code`。

| 代码 | 含义 |
| --- | --- |
| `input_unavailable` | 输入设备或通道不可用。 |
| `prompt_failed` | 文字展示或播报失败。 |
| `session_timeout` | 整轮问答超出总时限。 |
| `expired_before_prompt` | 提醒已接收，首次问候开始前已过有效期。 |
| `interrupted` | 重启或抢占导致流程中断。 |

个性化模块按流程故障处理这些结果。下面是另一个事件的错误回传示例。该提醒在 08:31:58 被接收，有效期到 08:32:00，模型在 08:32:01 准备首次问候时发现已过期。

```json
{
  "schema_version": "2",
  "event_id": "ce220c0e-4a71-4f1b-9dea-847ae12c2de7",
  "revision": 1,
  "status": "error",
  "error_code": "expired_before_prompt",
  "timestamp": "2026-11-24T08:32:01+08:00"
}
```

两个消息的 `timestamp` 差值表示“触发异常到产生结果”的时间，包含排队和问候时间。`prompted_at` 到结果产生的差值也只是首句问候后的流程耗时，可能包含追问；不能当作精确的老人回答延迟。进程内超时使用单调时钟，避免校时导致等待时间变化。

## 5. 问候、超时与模型兜底

以下为首轮联调建议默认值，双方实现时使用同一配置，并在联调记录中注明；不是已经验证的设备性能指标。

- 问候生成最多等待 10 秒；模型报错、超时或输出不可用时，立即改用固定话术。
- 一轮最多展示或播报 2 次，包含首次问候、无响应重试和听不清追问；它们共用次数上限。
- 每次问候展示完成或播放结束后，最多等待回答 20 秒。仅在输入通道健康时开始等待。等待期间通道失效且尚未取得有效回答时，结束本轮并回传 `error/input_unavailable`。
- 每次收到输入后的分类最多等待 5 秒；超时或失败视为“无法理解”，在仍有次数和时间时追问，否则回传 `unclear`，不得推断为 `ok`。
- 从本地模型首次记录接收成功开始，主动问答最多 90 秒，包含等待启动、生成、播报、等待回答和分类。达到总时限且尚无结果时，结束主动问答并保存 `error/session_timeout`。此前已收到、仍在 5 秒分类时限内的输入，若随后确认是求助，按 §6 回传更新。
- 首次展示或播报前，检查整轮时限和 `expires_at`。整轮已超时按 `session_timeout` 处理；否则，当前时间达到 `expires_at` 时结束本轮并回传 `error/expired_before_prompt`。已启动的一轮按 90 秒总时限运行。

处理顺序：

1. 可靠识别为 `needs_help` 后，立即按 §8 持久化并尝试发送，同时结束主动问候。求助一旦保存，超时或重启处理沿用该结果。
2. 明确回答 `ok` 时回传并结束主动问候。
3. 无回答或回答不清楚，在共用次数上限内追加一次问候；到限后，整轮曾收到回答但仍无法理解则回传 `unclear`，整轮均无回答才回传 `no_response`。
4. 麦克风不可用、播放失败、被对讲抢占等情况，返回相应 `error`，不伪造老人回答。

第一轮没有语音设备时，文字界面显示成功等价于问候交付，输入框或模拟输入等价于回答通道；验收记录须标明模拟或文字模式，不写成真实语音完成。

## 6. 回答更新与求助优先

- 相同事件、相同 `revision`、相同内容是重复投递，只处理一次；相同版本内容不同是协议冲突，拒绝并记录诊断。
- 本地模型按事件串行保存结果。首个结果为 `revision: 1`，发生本节允许的状态变化时加 1。同一回答的重试沿用已保存的版本。接收方允许版本跳号到达，保留结果历史，并用最高已接收版本更新当前结果。
- 迟到回答关联窗口从**首个结果产生时间**起算，持续 5 分钟。后续 `revision` 不延长窗口。由本地模型按**实际收到输入的时间**判断，收到时间早于窗口截止点且能明确关联到该事件时，才按迟到回答处理。这段时间只处理已有输入渠道送达的回答。
- 本地模型必须持久化首个结果产生时间、迟到回答窗口截止时间和当前 `revision`，并与结果及待发送记录保持一致。重启后沿用原窗口与版本，不重新开始 5 分钟窗口，也不将版本重置为 `1`；无法可靠恢复窗口剩余时间时，不擅自延长窗口，明确求助按本节的独立求助入口或人工流程处理。
- 窗口内收到的明确回答可以把 `no_response`、`unclear` 或 `error` 更新为 `ok` 或 `needs_help`，也可以把 `ok` 更新为 `needs_help`。迟到回答同样使用 5 秒分类时限。§5 中先收到输入、后确认求助的情形，按同一事件更新 `session_timeout` 结果。对已保存的 `needs_help`，重复求助沿用原结果。个性化模块按事件和版本接收更新，HTTP 到达时间不用于计算回答窗口。
- `needs_help` 一旦被接收，求助标记保持；后续 `ok`、`unclear`、`no_response`、`error` 均不得自动解除。解除由个性化模块或人工按单独规则决定。
- 已登记事件的有效 `needs_help` 即使以较低版本到达，也须保留求助事实。接收方保留当前结果版本，并按事件登记一次待处置任务；结果去重记录、求助标记和待处置任务一并保存后再确认。
- 超出关联窗口或无法确认归属的输入，不硬绑旧事件；明确求助交给独立求助入口或人工流程，不能静默丢弃。该入口未实现时须列为未完成项，不宣称支持任意时间的迟到求助。

例如，08:30 产生 `revision: 1` 的 `no_response`，08:34 收到“我起不来”，保存 `revision: 2` 的 `needs_help`。即使网络到 08:40 才恢复，个性化模块收到这条求助后仍应登记求助。如果版本 2 比版本 1 先到，后到的版本 1 只进入历史。

## 7. 首轮传输与确认

首轮建议使用本机 HTTP JSON，两个模块各自提供一个接收入口；具体端口通过配置提供，不在仓库写真实访问地址或凭据。文字／模拟联调也使用相同载荷。

- 个性化模块 → 本地模型：`POST /personalization/v2/reminders`。
- 本地模型 → 个性化模块：`POST /personalization/v2/results`。
- 路径是本稿建议的新接口，不能当作现有板端 API 直接调用。
- 个性化模块在**首次发送提醒前**保存事件及设备关联。结果匹配已登记事件即可接收，即使提醒回执尚未收到。
- 单次 HTTP 请求超时建议 3 秒。接收方在校验并保存后尽快确认，问答异步执行。
- `200` 回执包含 `schema_version`、`event_id`、`disposition`，结果回执还包含 `revision`。发送方须核对协议版本、事件 ID、适用于该请求的 `disposition`，以及结果回执中的版本号。回执缺字段、内容不匹配或无法解析时，按「未确认」记录诊断并按 §8 补发。各取值按下表处理。

| `disposition` | 提醒回执 | 结果回执 |
| --- | --- | --- |
| `accepted` | 本次接收并保存了新提醒。 | 本次接收并保存了此前未记录的结果版本。较低版本按 §6 处理。 |
| `duplicate` | 此前已接收并保存了相同的提醒。 | 已保存过同一版本且内容相同。 |
| `expired` | 该提醒此前未被接收，到达时已过期。发送方停止补发。事件仍无接收回执和有效结果时，记录「过期未接收」。 | — |

提醒接收方先校验载荷，再检查已有接收记录。当设备和事件 ID 匹配时，相同内容回 `duplicate`，内容冲突回 `409`。查不到接收记录时，先检查是否过期，再按 §8 预留问答名额并保存接收状态。已接收后、启动前的过期通过结果回传。

- `400` 表示格式或枚举非法；`404` 表示结果找不到已登记事件；`409` 表示同键内容冲突；`422` 表示协议版本不支持。这些错误停止原样重发，交由开发者排查。
- 请求超时、连接失败、`429` 或 `5xx` 可重试；接收方忙且尚未记录新提醒时应返回 `503`，不提前确认。
- HTTP 确认只证明本模块接收，不代表老人回答、报警完成或 App 收到消息。MQTT Broker 的发布确认同样不能替代业务处理确认。

后续改用 MQTT 或进程内队列时复用字段与处理规则，另补传输适配约定。异机部署须另行落实设备绑定、认证与加密；本机接口不得直接暴露为公网无认证接口。

## 8. 重发、去重与重启

- 所有重发保持原载荷不变，包括 `event_id`、`revision` 和时间；不能通过换 ID 或刷新时间延长旧提醒生命。
- 提醒去重键为“绑定设备 + reminder + event_id”；结果去重键为“绑定设备 + result + event_id + revision”。两种消息不能共用一个只有 `event_id` 的去重集合。
- 模型在同一次本地事务中完成去重确认、预留唯一的主动问答名额和保存「已接收、待启动」状态，保存成功后再回 `accepted`。执行者在首次实际展示或播报前独占推进到「可能已启动」。重复投递只返回回执，结束问答后可释放名额，结果补发在后台继续。
- 提醒首次失败后按 5、15、30 秒间隔重发，之后每隔 30 秒重试。每次发送前检查期限，到 `expires_at` 停止。收到有效的接收回执或结果时结束提醒重发。到期仍无回执和结果时记录「送达未确认」。后续收到有效结果时更新事件进度。已有结果时，迟到的提醒回执只用于诊断，事件进度以结果为准。
- 本地模型在一次本地事务中保存结果、版本和待发送记录。每个待确认版本独立补发，后续版本入队时保留尚未确认的早期版本。结果首次失败后按 5、15、30 秒间隔重发，之后每隔 60 秒重试。每个版本须在首次保存后 24 小时内补发，同时受下述事件补发截止时间约束。任一期限到达时停止补发，保留失败记录并标记待处理。
- 发送记录、接收去重和结果更新须能跨进程重启恢复。首轮可用本地 SQLite。事件索引、设备关联及去重记录至少保留到下列两个时间点中较晚者。
  1. 本模块首次保存该事件后 7 天。
  2. 事件补发截止时间。从提醒的 `expires_at` 起，加上整轮时限、迟到回答窗口、一次分类时限和 24 小时补发期。按首轮参数，合计为 24 小时 6 分 35 秒。两个模块按同一组联调参数计算该时间。
- 本模块仍有等待确认的结果或未完成的求助处置时，继续保留对应记录。个性化模块按上述截止时间保留匹配所需信息，即使网络中断期间看不到模型的待发送队列。

模型重启后按已保存的状态恢复。

| 保存状态 | 恢复方式 |
| --- | --- |
| 已保存结果 | 在补发期限内按原载荷和原 `revision` 补发尚未确认的结果，包括已保存的求助。 |
| 已接收，确定未启动且没有结果 | 按首次接收时间重新核对剩余总时限与提醒有效期。两个期限都满足时才启动；整轮超时回传 `session_timeout`，否则提醒到期回传 `expired_before_prompt`。无法确认剩余时间时回传 `interrupted`。 |
| 可能已启动且没有结果 | 结束中断的问答，使用 `revision: 1` 记录并回传 `error/interrupted`。 |

首次问候可能已经执行时，恢复流程只回传已保存结果或中断状态。恢复时已达到事件补发截止时间的，诊断和求助结果保存在本地待处理记录中。联调时要覆盖「标记已写入、播报尚未执行」及「已播报、结果尚未保存」两个关机点。

新提醒到达时，若已有问答占用名额，或音频资源被占用且无法启动，返回 `503`。已接收提醒的重发仍按 §7 确认。

## 9. 与现有链路的关系

- 本接口的 `response` 是对话理解结果，不自动等价于家属标注的误报／漏报反馈，也不直接驱动个体阈值学习。
- 若接入现有 care 事件，沿用已有稳定 `event_id` 并由适配层补齐人物、模型和版本作用域；不能把本稿直接覆盖到已有 care 消息或绕过现有模式门禁。
- 固定话术、模拟回答通过，只能证明接口流程可运行。板端性能、真实语音、断网对话、App 收到提醒和真实数据接入分别验收。
- 示例仅用虚构作息。真实录音、转写、作息、设备私密标识、密钥和模型文件不提交公开仓库；日志只保留必要诊断，不默认记录老人原话。

## 10. 联调验收清单

首轮使用文字／固定话术与模拟回复，记录输入、期望、实际结果和运行模式：

1. 正常回答 `ok`：回传成功，事件与版本一致。
2. 明确求助：立即回传 `needs_help`，不追加问候；重复投递只触发一次处置。
3. 听不清后仍不清楚：最多 2 次问候，最终 `unclear`。
4. 两次都无回答：输入通道健康，最终 `no_response`。
5. 先无回答、再听不清：不超过共用次数上限，最终 `unclear`。
6. 模型生成超时或报错：切换固定话术；分类超时按无法理解处理，不回 `ok`。
7. 麦克风／播报失败、总超时或对讲抢占：回传相应 `error`，不伪装为 `no_response`。
8. 同条提醒重发，包括到期后才收到重发包，已接收的同一载荷均回 `duplicate`。同键改动内容回 `409`。重启后，可能已启动且缺少结果的事件回 `error/interrupted`。
9. 先收到 `no_response`，本地模型在窗口内收到明确求助并保存新版本。分别模拟结果晚于窗口到达、两个版本乱序到达和求助重复到达，均应保留求助，每个事件只登记一次处置。
10. 回执丢失，发送方到期记录「送达未确认」。若模型的有效结果先到或之后到达，均成功关联到发送前已保存的事件。
11. 首次到达已过期时回 `expired`。已接收但直到过期才准备启动时，回传 `error/expired_before_prompt`。这两条路径的问候次数都为零。
12. 已保存 `needs_help` 但还未确认送达时重启，恢复后使用原版本和原载荷补发。结果超过补发期限时保留失败状态。
13. 未知提醒类型使用通用问候并据实分类。未知协议版本明确拒绝。
14. 提醒与回复共用事件 ID，两种消息各自正常接收。
15. 回执缺失版本号、事件 ID 不符、或 `disposition` 与接口类型不匹配。发送方保留待确认记录，按原载荷补发。已收到有效结果时，迟到的提醒回执不覆盖结果。
16. 交换 JSON 字段顺序、改变格式空白、把时间换成同一时刻的其他时区表示，接收方仍回 `duplicate`。改动 `reason` 时回 `409`。省略 `device_id` 和写出同一默认设备使用同一个去重键，已经接收后改变字段有无返回 `409`。
17. 两个不同事件同时请求问候，只接收一个，另一个回 `503`。获准事件的重复投递回 `duplicate`。插入等待期间的输入故障，确认回传 `error/input_unavailable`。
18. 分别模拟求助先保存和整轮超时先保存。前者重启后补发原结果、原版本和原时间；后者在超时前已收到的输入于分类时限内确认为求助时，保存新版本。接收端在规定保留期内仍能匹配补发结果。达到事件补发截止时间后重启，保留本地待处理记录。
