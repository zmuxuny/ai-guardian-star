# 人脸特征向量与严格头姿三照片录入设计

## 1. 意图

将人脸登记从“开发板持久化 JPEG，再由启动过程提取特征”改为“照片只在 App、云端转发进程和开发板内存中短暂存在，开发板仅持久化版本化特征向量”。同时把个人页现有的点击即拍即传改成独立、可确认、可重拍的三照片录入流程。

核心目的：减少生物照片持久化范围，让用户在上传前明确看到姓名和照片，并保持当前 ArcFace 识别效果以及 CPU 后备能力。

## 2. 当前事实

- App 使用前置系统相机生成 `cacheDir/face_upload_temp.jpg`，上传结束后在 `finally` 中删除。
- 云端 `/api/face/enroll` 只读取上传字节并转发，当前代码不写云端文件或数据库。
- 开发板目前把 JPEG 同时写入 `known_faces/<name>/` 和 `t_face_feature.feature_blob`；后者名称虽为特征，实际仍是 JPEG。
- `FaceLibrary` 从 JPEG 重建 ArcFace/CPU 特征、样本项和身份中心；ArcFace 是主路径，CPU 特征与 LBPH 是后备路径。
- 当前个人页直接弹提示并调用相机，姓名实际回退为账号昵称，拍完立即上传，没有姓名输入页和照片确认页。

## 3. 已选方案

用户选择：一次引导拍摄正脸、左侧脸、右侧脸；App 对实时预览执行严格头姿、单人脸、完整度、清晰度和活体门禁；每张照片生成 ArcFace NPU 特征和 CPU 后备特征；开发板只保存特征向量，不保存照片。

未采用：

- 只存 ArcFace：体积更小，但 NPU 模型不可用时失去 CPU 后备能力。
- 特征加密照片：便于未来重新提取，但不符合删除照片的隐私目标。

## 4. 目标与非目标

### 目标

- App 从“人脸信息”进入独立 `FaceEnrollment` 页面。
- 姓名必填且在调用相机前确认。
- 依次采集三张照片；每张返回页面预览，可重拍。
- 三张齐全后才允许最终确认上传。
- 拍摄确认必须同时通过头姿角度、稳定窗口、人脸完整度、清晰度、单人脸和活体检测，不能只凭转头角度放行。
- 云端和开发板接口以一次批量请求完成登记，避免部分成功。
- 特征持久化事务成功后不在开发板创建 JPEG。
- App 临时照片在成功、取消或页面销毁时删除；可恢复的上传失败仅在当前页面会话内保留，供用户直接重试，退出页面即删除。
- 保持当前 ArcFace 相似度、身份间隔和多样本匹配语义。
- 保留无照片依赖的 CPU 向量后备匹配。
- 旧 JPEG 迁移必须先完整生成并验证向量，再删除照片。

### 非目标

- 本次不调整识别阈值、陌生人投票、人体跟踪或告警策略。
- 不在云端保存、展示或下载人脸特征。
- 不声称特征向量匿名；它仍属于敏感生物特征。
- 不自动部署生产服务器或开发板，不自动删除历史备份中的数据。
- 不保证未来更换 ArcFace 模型后旧向量继续兼容；模型改变时需要重新录入或运行有照片来源的受控迁移。

## 5. App 交互设计

### 入口

个人页“人脸信息”行保留现有图标、颜色与副标题位置，点击行为改为 `pathStack.pushPathByName('FaceEnrollment', null)`。

### 页面状态

1. `name`：标题“录入人脸”，显示姓名输入框、隐私说明和底部“开始拍摄”。空值、全空格、超长或含路径/控制字符时就地提示。
2. `liveness`：姓名确认后执行一次前置摄像头动作活体检测；活体失败、取消或超时不能进入拍摄。活体组件返回的最佳活体 `PixelMap` 只在本次会话内存中保留，用于确认后续三张照片与活体是同一人；不写缓存、不上传，也不把它当作三张姿态照片。
3. `capture`：使用 App 内自定义前置相机预览，按正脸、左侧脸、右侧脸采集。预览上实时显示头姿角、质量状态和单一纠正提示；全部门禁持续满足后才允许拍摄确认。
4. `review`：展示三张照片及角度标签；每张可“重拍”；底部“确认录入”是唯一高强调动作。
5. `uploading`：锁定返回、重拍和重复提交，显示明确进度文案。
6. `success`：提示“人脸特征已安全保存到开发板”，清理临时文件并返回个人页。
7. `error`：保留仍在 App 沙箱中的三张预览供重试；若用户退出则全部删除。

### 严格头姿门禁

角度使用未镜像的相机图像坐标系中的标准化值，单位为度：

- 正脸：`-15 <= yaw <= 15`
- 左侧脸：`yaw <= -25`
- 右侧脸：`yaw >= 25`
- 所有姿态：`-20 <= pitch <= 20`
- 所有姿态：`-15 <= roll <= 15`

左、右侧脸的 yaw 按用户给定规则使用单侧阈值，不擅自增加最大侧转角。极端侧脸仍必须通过完整度、遮挡、清晰度和静态复验；若后续真机数据证明需要 `-45/45` 一类上限，必须另行确认后再改业务规则。

单帧命中不能放行。目标角度和全部质量条件必须连续稳定至少 500 ms，且覆盖至少 5 个不同预览帧的有效分析样本，之后才启用拍摄按钮；任一条件失效立即禁用。稳定窗口使用帧采集时的单调时钟，不使用推理结束时间；相邻有效样本间隔超过 300 ms、最后结果距点击超过 300 ms、应用切后台、相机会话重建或显示方向变化时，窗口立即清零。拍下的静态照片再执行一次完整校验，静态照片不合格则不进入预览，回到当前姿态继续拍摄。

提示按以下优先级只显示当前最需要纠正的一项，避免同时给出互相竞争的指令：

1. 未检测到人脸或检测到多人。
2. 活体未完成或失败。
3. 人脸超出安全框、关键部位被遮挡或完整度不足。
4. 模糊、过暗、过亮或脸部尺寸不合格。
5. `roll` 不合格：提示“请保持头部水平”。
6. `pitch` 不合格：按经真机标定后的符号方向提示“请抬头”或“请低头”。
7. `yaw` 不合格：正脸根据偏离方向提示回正；左/右侧脸提示“请继续向左转头”或“请继续向右转头”。

人脸完整度至少包含：恰好一张人脸、人脸框完整落在安全区域、脸部尺寸位于可用范围、五个关键点（双眼中心、鼻尖、左右嘴角）均存在且几何关系合理、Core Vision 遮挡结果为未遮挡。Core Vision 只有整体人脸置信度，没有逐关键点置信度，因此不能声称逐点置信度门禁；若真机证明五点和整体遮挡不足以可靠识别局部遮挡，则 Phase 0 必须引入共享关键点/头姿模型。清晰度至少包含：对焦/模糊、亮度、过曝和欠曝。具体质量阈值进入版本化配置，并以目标手机真机样本校准，不能只凭模拟器或单一机型拍脑袋写死。

### 镜像与左右方向校准

- 前置预览允许镜像以符合用户习惯，但分析输入必须统一转换为未镜像坐标；UI 镜像和算法坐标不得共用同一个未经说明的符号约定。
- 分析和最终上传像素先统一旋转为竖直、未镜像、无 EXIF 方向依赖的规范图，再运行检测器。头姿输出先记录为原始 `yaw/pitch/roll`，再通过显式的轴交换、`yawSign/pitchSign/rollSign` 和零点偏移标定转换为业务角度。
- 真机验收必须由测试人员实际向物理左侧和右侧转头，确认左侧最终为负、右侧最终为正；若设备/前摄输出相反，只修改标定层，不修改业务阈值。
- 标定结果按设备型号、系统版本、相机 ID、传感器方向、检测器版本和预处理版本记录；找不到匹配标定或校准自检失败时禁止录入，不能猜测左右方向。

### 视觉方向

- 模式：Operate，任务优先。
- 继承当前 App 的浅蓝页面背景、白色圆角卡片、深色主标题、蓝色主按钮、细分隔线及现有深色模式。
- 顶部使用与 `Profile`、`MyAddress` 一致的返回与标题结构，不引入新的全局视觉语言。
- 三张照片采用等宽预览槽；完成状态用文字和图标共同表达，不只依赖颜色。
- 底部主按钮保持至少 44vp 点击高度；姓名输入在软键盘弹出时仍可见。
- 失败文案区分权限拒绝、用户取消、图片过大、照片不可用、设备离线、会话失效和上传失败。

### 相机与头姿实现约束

- 系统 `CameraPicker` 无法承载实时角度提示和确认门禁，因此录入页改用 Camera Kit 自定义会话：一条 `XComponent` PreviewOutput 用于显示，一条 `ImageReceiver` PreviewOutput 用于按节流频率取最新帧，再加一条 `PhotoOutput` 拍照。三路输出组合必须通过目标前摄的 `getSupportedOutputCapability`、逐路 `canAddOutput` 和 `commitConfig` 真机探针，不能只凭 API 存在假定设备支持。
- 实时分析只保留最新帧，上一帧仍在推理时直接丢弃新任务，禁止积压队列；初始目标为 5–10 次/秒，并以真机帧率、温升和耗时验收调整。
- 本机 API 24 SDK 的 `@hms.ai.face.faceDetector.d.ts` 已静态确认 `FacePose.yaw/pitch/roll` 为 `[-180,180]` 的连续数值，并提供五点、人脸整体置信度和可选遮挡结果。Phase 0 不再验证“API 是否存在”，而是验证目标机 syscap、符号/旋转约定、稳定性、精度和端到端性能。
- `faceDetector` 只接受 RGBA_8888 PixelMap。技术探针必须把 ImageReceiver 输出到旋转、裁剪、颜色转换和 PixelMap 创建的时间全部计入端到端延迟；P95 必须小于最终选定的分析周期，并记录 P50/P95/P99、10 分钟掉帧、内存和温升，不能只测 `detect()`。
- Vision Kit 活体检测会临时占用相机。活体回调后必须释放组件并带有限重试地创建自定义 CameraSession，覆盖 `camera busy`。`mPixelMap` 必须在三张照片完成同人比对或会话结束后显式释放；`securedImageBuffer/certificate` 的设备安全验证不纳入本阶段，除非后续明确要求抵抗被篡改客户端。
- App 使用本地 `faceComparator` 将活体 `mPixelMap` 与三张最终规范 JPEG 的解码 PixelMap 分别比对；任一不是同一人则拒绝该照片。这样活体证明绑定到最终登记主体，而不只是证明此前曾有人通过活体。
- App 端负责实时体验门禁；开发板在最终静态照片上独立复算头姿与质量，不能只信任 App 随请求上传的角度元数据。当前开发板检测器没有数值头姿能力，因此 Phase 0 必须先定型板端头姿/关键点模型和运行时：优先选择 App/板端可共享的轻量模型；若 App 保留 Core Vision、板端采用另一模型，则必须用同一校准集建立两端误差分布和安全判定规则。该模型未定型前，不进入完整实现。
- 若目标设备不支持“显示预览＋分析预览＋拍照”三路组合，Phase 0 必须先验证并选定单分析 Surface 兼顾显示、降低 profile 或其他不降低严格门禁的回退方案；不允许静默退回 CameraPicker 或取消实时校验。

## 6. 数据与模型设计

### 身份表

`t_face_identity`

- `user_id TEXT PRIMARY KEY`
- `name TEXT NOT NULL`
- `created_at INTEGER NOT NULL`
- `updated_at INTEGER NOT NULL`

### 特征表

`t_face_embedding`

- `sample_id TEXT NOT NULL`
- `user_id TEXT NOT NULL`
- `pose TEXT NOT NULL`：`front` / `left` / `right` / `legacy`
- `backend TEXT NOT NULL`：`arcface` / `cpu`
- `variant_index INTEGER NOT NULL`
- `model_id TEXT NOT NULL`
- `vector_dim INTEGER NOT NULL`
- `vector_dtype TEXT NOT NULL`：固定 `float32-le`
- `feature_blob BLOB NOT NULL`
- `quality_json TEXT NOT NULL`
- `created_at INTEGER NOT NULL`
- 主键：`(sample_id, backend, variant_index)`
- 外键：`user_id -> t_face_identity.user_id ON DELETE CASCADE`

特征写入前必须归一化、检查维度、有限值和范数；读取时必须校验 `backend/model_id/vector_dim/vector_dtype/blob length`。任何不兼容向量都拒绝加载，不能与当前模型混比。

### 模型标识

- ArcFace：识别模型文件内容 SHA-256，加最终输入布局、dtype、输出维度、裁剪/增强/尺度变体版本。
- CPU：CPU 特征算法版本常量，加 Haar 裁剪、灰度均衡、128×128 和描述子版本。
- 服务启动时只加载与当前模型标识一致的向量。
- 向量序列化固定为显式小端 `<f4`，不能依赖开发板本机字节序。

### 图库内存结构

`FaceLibrary` 新增从数据库特征行构建 `entries` 和 `centroids` 的路径。内部身份键必须是 `user_id`，`name` 只用于显示，避免两个同名账号被合并。ArcFace 继续使用每个身份的最佳样本相似度和第二名间隔；CPU 使用已保存的 CPU 特征距离。LBPH 不再作为无照片模式的持久化后备，避免暗中依赖 JPEG。

## 7. 登记事务

1. App 在自定义相机预览中完成活体同人绑定、严格头姿、稳定窗口、单人脸、完整度和清晰度门禁。
2. 每次拍照后严格执行同一顺序：旋转/去镜像标准化 → 缩放并重新编码 JPEG → 从最终 JPEG 重新解码 → App 静态头姿、质量和活体同人复验 → 用同一最终 JPEG 预览和上传。单张不超过 1.5 MiB、整批不超过 5 MiB。
3. App 与云端使用版本化、带长度边界的二进制登记信封，不使用会隐式 spool 到临时文件的 multipart 解析器。信封包含姓名、三个唯一 pose、App 复验角度/质量摘要、检测器版本和三段 JPEG 字节。
4. Nginx 对该接口关闭请求体缓冲；云端从受限流读取信封、用认证账号生成 `user_id`、重新封装后直接转发，不创建 `request.files`、`UploadFile` 或临时文件。
5. 开发板通过受限 `Request.stream()` 读取信封，在内存中解码三张照片，独立复算并严格校验 pose、单人脸、完整度和清晰度。
6. 对每张照片生成与当前图库相同的人脸尺度变体，并为每个变体生成 ArcFace 与 CPU 特征和质量元数据。
7. 先用候选特征在内存构建、验证完整 staged 图库；不得在提交数据库后再执行可能失败的重建。
8. staged 图库验证成功后，在一个 SQLite 事务中替换该 `user_id` 的身份与特征行；提交后只执行不可失败的内存 publish 和 revision 切换。
9. 任一步失败都不改数据库和已发布图库。请求结束后释放图片对象和可变缓冲区；Python/系统运行时内存无法承诺物理“安全擦除”，但不产生持久化照片文件。

## 8. 旧数据迁移

- 提供显式的一次性迁移命令，不在普通服务启动时静默删除照片。
- 数据库启用 `PRAGMA foreign_keys=ON`，通过 `PRAGMA user_version` 管理 schema；迁移建立身份、特征和必要索引后再切换版本。
- 迁移先盘点 `known_faces` 与旧 `t_face_feature`，按身份提取 ArcFace/CPU 特征并写入暂存事务。
- 每个身份至少生成一组兼容向量；数量、维度、模型标识和加载结果全部验证后才提交。
- 提交后重新加载图库并执行已登记样本的离线自匹配检查。
- 验证通过后删除 `known_faces` JPEG，并把旧 `feature_blob` 图片列清空或删除旧表。
- 迁移提供 `--dry-run`、代次标识、可重复执行清单和“向量已生效但部分 JPEG 删除失败”的继续清理命令；SQLite 提交与文件删除不伪装成一个原子事务。
- 部署前的照片回退备份是临时的：设备验收通过并得到用户确认后删除；不能把含照片的备份长期保留成新的隐私副本。
- 普通文件删除不能保证闪存物理块不可恢复；本设计承诺删除文件系统和数据库中的可访问副本，不作物理介质安全擦除承诺。

## 9. 云端和 App 数据边界

- 云端不新增照片、特征或 multipart 原文日志。
- 响应继续设置 `Cache-Control: no-store`。
- 反向代理对登记接口设置 `proxy_request_buffering off`，不得缓存或写入 `client_body_temp`；测试覆盖正常、超限和异常中断后无临时文件。
- App 只把三张照片放在私有 cache 目录，文件名使用随机会话 ID，禁止进入系统相册、备份和日志。
- 上传成功、放弃、退出和账号注销路径统一调用清理函数。
- 当前账号仍只登记一个被照护身份；同账号再次确认录入会以事务方式替换该账号原有全部特征，不扩展为多人名册。

## 10. API 契约

`POST /api/face/enroll`，`Content-Type: application/vnd.ai-guardian.face-enrollment-v1`

- 信封：`name`、三个唯一的 `pose`、App 复验角度/质量摘要、检测器版本和三段带长度的 JPEG；顺序无关，pose 必须恰好是 `front/left/right`。摘要仅用于诊断，开发板必须从照片独立复算。
- 限制：恰好 3 张；单张不超过 1.5 MiB；整批信封不超过 5 MiB。
- 成功返回：`success/recognitionStatus/sampleCount/embeddingCount/hint`，不返回向量。
- 验证失败：400，并携带具体 `pose`；并发冲突：409；总大小超限：413；开发板不可用：503；认证状态沿用现有 401/403。云端、bridge 和 App 原样保留 409 与 pose。

## 11. 失败与并发

- 同一账号并发登记由开发板按 `user_id` 串行化，后到请求可拒绝为 409。
- 三照片双后端推理放入受控工作线程，复用 ArcFace `_infer_lock`、ACL context 绑定和全局 NPU 执行锁；事件循环不得同步执行重推理。
- 图库加载采用现有 staged/publish 模式：新图库完整后才替换旧图库。
- 登记期间识别继续使用旧 revision；完成后 revision 增加，进行中的旧识别结果不得覆盖新图库结果。
- 任一照片不可用时整批失败，App 定位到对应角度并允许重拍。
- NPU 模型不可用时不接受新的“完整双向量登记”，避免只写半套数据；现有 CPU 向量仍可用于降级识别。
- App 为每次录入创建随机会话目录和 session token；异步相机结果必须匹配当前 token，页面销毁后不能回写状态。
- 应用进入录入页时清除该命名空间中过期的遗留目录，覆盖崩溃或强杀；调起系统相机导致应用暂时后台时不能误删当前会话目标文件。

## 12. 测试与验收

### 自动化

- 特征 float32 序列化/反序列化、维度和模型标识拒绝测试。
- 三照片登记成功不创建 JPEG、事务替换和失败回滚测试。
- 同一身份多向量加载、ArcFace/CPU 后备识别测试。
- 旧照片迁移成功后删除、失败时照片保留测试。
- 云端三文件数量、大小、MIME、认证、no-store 和无落盘转发测试。
- Nginx、Flask 和 FastAPI 在正常、超限及中断请求下均不产生登记请求临时文件。
- App 抽取纯状态规则，覆盖姓名校验、三角度完成条件、重拍、最终确认、失败重试和退出清理。
- App 头姿规则单元测试覆盖所有阈值边界：`-15/15/-25/25/-20/20`、`-15/15`，稳定窗口中断后必须重新累计。
- 提示优先级、镜像转换、相机旋转、`yawSign/pitchSign` 标定和未知标定拒绝测试。
- 静态照片复验与实时预览结果不一致时拒绝；开发板复验不信任 App 角度摘要。
- HarmonyOS release 构建与现有 Python/Node 测试全量回归。

### 设备验收

- 正脸、左右侧脸采集和预览；角度未达标时按钮不可用，达到阈值但不足 500 ms/5 个样本仍不可用。
- 分别制造 yaw、pitch、roll、多人、遮挡、出框、模糊、过暗和活体失败，确认提示正确且不能绕过。
- 在至少两台目标手机上测试物理左转/右转和前置预览镜像，确认业务角度左负右正；相机 ID 或设备无标定时必须拒绝录入。
- 拒绝权限、取消活体、取消拍照、重拍、上传失败、退出清理。
- 开发板数据库只有向量和元数据，`known_faces` 无新增 JPEG；云端应用目录和数据库无照片副本。
- 已登记人员在正常角度和侧脸下识别；未登记人员不误认为已登记身份。
- NPU 正常和 CPU 降级两种路径验证。
- 重启服务后无需 JPEG 仍能加载图库并识别。

## 13. 交付边界

- 代码先落在 `wip/codex-20261103-face-vector-enrollment` 独立 worktree。
- Phase 0 只实现不接业务上传的真机技术探针：Core Vision 数值角/遮挡/五点、动作活体与相机释放、`faceComparator` 同人绑定、三路相机输出、规范图转换性能，以及板端头姿模型定型。Phase 0 通过后才进入 Phase 1 的完整 UI、协议、数据库和迁移实现。
- Phase 0 通过标准至少包括：API 24 构建成功；两台目标手机 syscap 可用；物理左负右正；三路输出成功；端到端 P95 小于分析周期；连续 10 分钟无不可接受掉帧/温升/内存增长；活体后相机可可靠重开；App 与板端对最终 JPEG 的角度误差带可建立；完整度门禁能拒绝遮挡和缺失关键部位。
- 未完成开发板迁移与真机验收前，不合并到共享分支，不 push，不部署。
- 生产部署遵循 `DEVECO_BUILD.md` 和项目“备份→最小修改→本地验证→push→部署”顺序。

## 14. 已确认的隐私与校验边界

1. 账号注销先尝试同步删除开发板向量；开发板离线时，云端建立只含 `user_id` 的可靠删除任务，账号可先注销，板端恢复后自动完成删除。
2. 正脸、左右侧脸采用本设计规定的严格数值头姿门禁，并叠加稳定窗口、完整度、清晰度、单人脸和动作活体检测；任一条件失败都不能确认。
3. 无法可靠映射到账号的旧 JPEG 阻塞自动删除并输出人工映射清单，不猜归属、不擅自删除。
4. 本阶段接受开发板 SQLite 明文 float32 特征，以 root-only 文件权限、最小备份和设备访问控制保护；数据库静态加密作为后续独立任务。
