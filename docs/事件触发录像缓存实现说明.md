# 事件触发录像缓存 · 实现说明（交接用）

面向后续接手的人或 AI。读完应能回答：这段代码怎么工作、怎么跑、怎么验证、还差什么、怎么接进服务。

## 一、要解决什么问题

异常行为（摔倒 `fall` / 久坐 `sit` / 陌生人 `stranger`）发生时，自动保存一段**包含事件发生前几秒**的视频。

"事件前几秒"不能靠检测到再开录——那时候画面已经过去了。所以必须**常驻一个内存环形缓冲**，平时只留最近 N 秒，触发时把缓冲里的帧倒进编码器。这是本功能与"连续录像"的本质区别。

## 三、关键设计决策（改之前先读这一段）

1. **复用 `RecordingManager`，不另写编码循环。** 每个事件片段创建一个独立的 `RecordingManager`，`segment_seconds` 设为 `event_clip_max_seconds + 5`，保证一个片段只产出一个 MP4。好处是存储配额检查、后端契约、`media_verified` 校验全部复用，不产生第二套实现。
2. **通过包装 `backend_factory` 拿 `segment_id`。** `RecordingManager` 不对外暴露它生成的 `recordings.id`。`_CapturingFactory` 在 `backend.start(metadata)` 时截获 `metadata["segment_id"]`，这就是入库的 recording id，无需回查数据库。
3. **`event_recordings` 新增表而不改 `user_version`。** 表用 `CREATE TABLE IF NOT EXISTS` 写在既有的建表脚本里，老库（`user_version=1`）下次打开就自动补上，不需要迁移、不需要重建。
4. **有界优先于完整。** 缓冲帧数和字节都设上限，超了就丢最老的并计入 `drop_reasons.pre_roll_evicted`。宁可少几帧，也不能让录像把内存吃穿。
5. **片段内重复触发只延时，不新开文件。** 一个"事件连续体"对应一个文件，多个事件 id 关联到同一条录像；总长受 `event_clip_max_seconds` 约束，触顶后 `capped=true`。
6. **帧 `shape` 必须随缓冲一起保存。** `FramePacket` 里存了 `shape`；`_submit` 用 `memoryview(data).cast("B", shape=packet.shape)` 还原成多维视图再交给 `RecordingManager`，否则后端会收到 `(n,)` 形状而无法推断分辨率。

## 四、配置项

在 `RecordingConfig` 上新增，均可通过 `AI_GUARDIAN_RECORDING_CONFIG` 指向的 JSON 覆盖：

| 字段 | 默认 | 范围 | 含义 |
| --- | --- | --- | --- |
| `pre_roll_seconds` | 5 | 0–60 | 事件前预录秒数；0 表示不预录 |
| `post_roll_seconds` | 10 | 1–600 | 事件后继续录制秒数 |
| `event_clip_max_seconds` | 120 | 1–3600 | 单片段总时长硬上限 |
| `cache_bytes` | 32 MiB | 1 MiB–512 MiB | 环形缓冲与片段待写队列的字节上限 |

约束：`pre_roll_seconds + post_roll_seconds ≤ event_clip_max_seconds`，否则构造即抛 `ValueError`。

**默认 `enabled=False`**，此时 `start()` 返回 `False`、`submit_frame()` 返回 `False`、`trigger()` 返回 `None`，不建目录、不起线程。

## 五、接口

```python
cache = EventClipCache(config, store, backend_factory)   # store 通常与连续录像共用一个 HistoryStore
cache.start()                                            # 启动工作线程
cache.submit_frame(frame, captured_at=ts, monotonic_at=mono, frame_id=i)   # 采集点每帧调用
cache.trigger("fall", payload={"score": 0.9})            # 告警点调用，内部建事件行
cache.trigger(event_id=已存在的事件id)                    # 或用已有事件，不重复建
cache.status()                                           # 观测：缓冲帧数、当前片段、丢帧原因
cache.stop(timeout=15)                                   # 收尾当前片段并退出
```

`trigger` 返回值：`{"event_id", "state", "extended", "pre_roll_frames", ...}`。
`status()["last_clip"]` 是最近一段的结论：`finalized / linked_events / written_frames / manager_state`。

## 六、接入位置（2026-10-22 已完成）

接线提交见 `docs/修改记录/2026-10-22-异常触发录像接线.md`。三处落点如下，改动仍需遵循最小修改：

1. **创建与生命周期**：`src/ascend_board_server.py` 的 `run_system()`，在音频线程启动之后、`inference_loop` 定义之前。`RecordingConfig.from_env()` 判断 `enabled`，为真才 `initialize_storage()` → `HistoryStore()` → `EventClipCache(config, store, create_backend)` → `start()`；整段包 `try/except`，失败只打印并保持关闭。关闭钩子在 `shutdown_event` 中 `cache.stop(15)` 并 `store.close()`。
2. **采集分流**：`src/ascend_main_other.py` 的 `AclLiteStreamDetector.__init__` 接受可选 `event_cache`，在 `_camera_reader_thread` 写入 `latest_frame` 之后调用 `submit_frame(frame, captured_at=now, monotonic_at=self.last_camera_frame_at)`。这是唯一摄像头成功采集点，别在别处再喂一次。
3. **告警触发**：`src/ascend_board_server.py` 中 `new_events = event_tracker.update(alerts, _now)` 之后，对 `fall / sit / stranger` 三类逐条 `event_cache.trigger(kind, at=_now, person_id=..., payload={"kind": kind})`。

三处都做了异常隔离：录像任何环节出错都只丢片段，不中断检测与告警。

**接线后仍需真实场景验收**：真实摄像头画面、NPU 检测并发、码率与容量、手机播放（`/recordings/{id}/video` 仍 503）。

## 八、已知坑（踩过的，别再踩）

1. **ffmpeg 必须显式 `-f mp4`。** `RecordingManager` 给后端的是 `xxx.mp4.partial`，ffmpeg 无法按后缀判断容器，会立刻退出，表现为 `BrokenPipeError`。
2. **队列字节要按分辨率给。** 640×480 bgr24 单帧 0.9 MB，`queue_bytes` 太小会在触发瞬间 `queue_full` 丢预录帧。
3. **合成纯色帧的码率没有参考价值。** 一个 3 秒片段只有 3.7 KB，别拿它算七天容量。
4. **`list_recordings` / `list_events` / `list_gaps` 返回的是 list，不是 `{"items": ...}`。** 只有 HTTP 接口层才包成 `items`。
5. **Windows 上临时目录清理可能报 `WinError 32`**，因为 SQLite 连接没关。测试里所有 `sqlite3.connect` 都要显式 `close()`。
6. **`Popen.communicate()` 会 flush 已关闭的 stdin。** 手动 `stdin.close()` 后再 `communicate()` 会抛 `ValueError`（它只捕获 `BrokenPipeError`），片段直接 `failed`。正确做法：关闭后把 `proc.stdin` 置 `None` 再 `communicate()`。假后端测不出这个问题，只有真实编码才暴露。
